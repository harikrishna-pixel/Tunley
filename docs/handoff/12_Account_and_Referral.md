# 12 · Account and Referral (V1.3)

Added in **V1.3** (Praba's decision: referral is a standard feature in every Marberx app; login is only for people who want the referral reward).

Screens: **46** Invite friends (signed out) · **47** Invite friends (signed in) · **48** Create account · **49** Sign in (+ 49b error) · **50** Reset password (+ 50b sent) · **51** Account · **52** Delete account · **53** Redeem invite code (+ 53b success, 53c invalid) · **23** Settings (Account row, Invite friends, Have an invite code?).

## 1. Principles

1. **Login is optional.** The app works fully without an account: convert, make ringtones, save, buy Pro, restore. Never ask for login anywhere else.
2. **Only the inviter signs up.** Login is requested only when a user taps **Invite friends / Get Pro free** (Settings 23 or Account 51).
3. **The invited friend never needs an account.** They redeem a code (from the link or typed on 53) against their anonymous app ID.
4. **Explain before asking.** Screen 46 shows the offer, the 3 steps, a locked link and *"Your account only keeps your invite link and free weeks safe if you change phones. Your files never leave your iPhone."* before any form.
5. **Pro subscriptions are tied to the Apple ID, not the account.** Login never affects purchase/restore.

## 2. Authentication (reuse the existing Bible-app API)

Email + password only (no social login). Because there is no third-party/social login, Sign in with Apple is **not** required by App Review.

| Item | Rule |
|------|------|
| Sign-up fields | First name, Last name, Email, Password |
| Validation | First/last name 1–50 chars; valid email; password ≥ 8 chars incl. a number. Show inline errors under the field, never only in a toast. |
| Existing email | "An account with this email already exists. Sign in instead?" with a Sign in link |
| Sign-in error | One generic message: "Email or password is incorrect" (don't reveal which) |
| Rate limiting | API locks after 5 failed attempts for 15 min; show "Too many attempts. Try again in 15 minutes." |
| Reset password (50) | Always show "If an account exists for X, you'll get a link" (no account enumeration). Resend allowed after 60 s. Reset link opens a web page (or the app via universal link) to set a new password. |
| Email verification | Verification email sent on sign-up. Account works immediately, but **inviter rewards are only granted after the email is verified**. Banner on 51 with Resend. |
| Session | Access + refresh tokens stored in **Keychain** (`flutter_secure_storage`). Auto-refresh; on refresh failure sign out silently. |
| Sign out | Clears tokens; app keeps working; Pro unaffected |
| **Delete account (52)** | **Required by Apple** for apps that allow account creation. Confirm with password. Deletes account, referral code, unused reward days. Files (in Tunely and the Tunely folder) and the App Store subscription are not affected (tell the user to cancel the subscription in Apple settings). Must work in-app, not by email. |
| Multi-app separation | Every auth and referral call sends **`app_id = "tunely"`**. Users, codes and referrals are scoped per app — a Bible-app account must not appear in Tunely and vice versa (unless you deliberately decide to share accounts — see Open Questions). |

## 3. Referral code

- Generated by the server **at sign-up** and returned in the response.
- Format: first name, accents removed, A–Z only, max 6 letters, uppercase + **2 random characters** → `ANNA7K`, `PRABA4M`. If the name gives fewer than 2 letters, use `TUNE` + 4 random → `TUNE7K2Q`.
- Character set for the random part excludes `0 O 1 I L`.
- Server guarantees uniqueness (case-insensitive) and runs a profanity check.
- User can switch to a fully random code once from screen 51 (privacy). Old code stops working for new redemptions.
- Invite link: `https://<domain>/i/<CODE>` (universal link + web fallback page with the offer and App Store button).

## 4. How the friend's code reaches the app

1. **Automatic (deferred deep link):** link service (Branch recommended — Firebase Dynamic Links was shut down in 2025) passes the code to the app on first open → screen 53 opens with the code prefilled and "Added from your friend's link".
2. **Manual (always available):** Settings › **Have an invite code?** → screen 53. Also offered once at the end of onboarding if no deep-link code was found ("Got an invite code?" link — not a blocking step).
3. If the app is already installed, the universal link opens 53 directly.

## 5. Rewards & states

| Event | Who gets what | When |
|-------|---------------|------|
| Friend redeems a valid code | **Friend: 7 days Pro** | Immediately (success state on 53) |
| Friend completes first successful conversion or ringtone | **Inviter: 7 days Pro** | Only if inviter's email is verified; otherwise held as "pending" until verified (max 30 days) |

Reward delivery: server calls **RevenueCat → grant promotional entitlement "pro" for 7 days** to the right app_user_id (inviter's RevenueCat ID is linked to their account at sign-in via `logIn(accountId)`). If not using RevenueCat, the server stores an expiry and the app's entitlement check reads it from `/me`.

Referral record states: `redeemed → qualified → rewarded`, or `rejected` (reason: invalid_code, self_referral, device_used, cap_reached, inviter_deleted).

Invite screen stats (47): **Friends joined** = qualified + rewarded · **Pro earned** = rewarded days · **Pending** = redeemed but not yet qualified / awaiting email verification.

## 6. Anti-abuse

- **One redemption per iPhone**, enforced with Apple **DeviceCheck** (2 bits per device survive reinstall) — implemented in the native plugin, verified by the server.
- No self-referral: inviter's account/app_user_id ≠ friend's; same DeviceCheck device can't be both.
- Cap: **10 rewarded invites per inviter per year** (configurable). After the cap, links still give the friend a week but the inviter gets nothing; screen 47 shows "You've reached this year's invite limit".
- Reward only after the first successful conversion — never for install alone.
- Never reward ratings or reviews (App Review rule).

## 7. Privacy & compliance

- Privacy label: add Contact info (name, email) and User ID — linked to the user, used for App Functionality. Update the Privacy Policy.
- Analytics never include email or name.
- Password never logged; HTTPS only; tokens only in Keychain.
- Data deletion via screen 52 and on request to support email.

## 8. Error & edge states

| Situation | UI |
|-----------|----|
| No internet on sign-up/sign-in/redeem | Inline: "You're offline. Connect to the internet and try again." (button stays enabled) |
| Server error | Inline error box + retry; never lose typed form data |
| Code invalid / already used on this device | 53 Invalid state (53c) |
| Friend already Pro (subscriber) | Accept code (inviter still qualifies after first conversion); show "You're already Pro — your friend still gets their reward when you make your first file." |
| Signed in on a second iPhone | Same account, same code, rewards follow the account |
| Account deleted while pending rewards exist | Pending rewards cancelled |

## 9. Where the invite is offered (never pushy)

| Place | Rule |
|---|---|
| Settings (23) | Always: Account row + Invite friends (Get Pro free) + Have an invite code? |
| Milestone (30) | Not in V1.3. Idea to test later: one quiet line "Invite a friend, you both get a week of Pro" |
| Result (09) | **Never** (keeps Result clean; ad break and Marberx card already live there) |
| Pro users | Still see Invite friends (they can earn time that stacks after their plan or gift the friend) |

The invite is never shown as a pop-up, never during a task and never in the same session as a paywall.
